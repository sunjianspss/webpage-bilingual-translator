# v0.1.6 - Translations That Survive Scrolling

A bug-fix release. Everything here is about a page finishing what it started:
translating a long article used to stop partway through for reasons that had
nothing to do with translation, and the message it left behind said only that
the task had been cancelled.

## Highlights

### Scrolling no longer cancels the translation

Reading along while a page translated would stop it. The status bar turned red,
said 翻译任务已取消, and the rest of the article stayed in English.

The extension binds a translation to the tab it started in and abandons it when
that tab navigates away, which it judged by the tab reporting status `loading`.
That turns out not to mean what it looks like. On a site whose router prefetches
pages, scrolling brings links into view, the router fetches their chunks, and
the tab's loading state flips and flips back — no navigation, no URL in the
event, the same document throughout. One scroll was enough.

A changed URL is the signal that actually means a document changed, and that is
all the listener acts on now. Nothing watches for reloads there any more and
nothing needs to: `pagehide` fires when a document is genuinely leaving, and the
page already reports it. If every signal somehow missed, what would linger is a
settings snapshot in session storage until the tab closes — much cheaper than
cancelling a translation that is still running.

Two narrower versions of the same mistake are gone with it. Clicking an entry in
an article's table of contents cancelled the page, because a fragment change
counted as leaving the document; translations are now bound to a document, and a
URL differing only after the `#` leaves them alone. And pressing the shortcut a
second time during a run cancelled the first one, because the guard meant to
refuse the second press read a status field that resets at the end of every
scan, so a press landing between scans went straight through.

### One lost batch no longer ends the page

A cancelled batch was fatal for the whole run: the workers stopped, and every
paragraph not yet translated stayed untranslated. That is correct when someone
presses cancel and wrong when the background task simply went missing — Manifest
V3 recycles the service worker, and `chrome.storage.session` does not exist on
Safari, so the record can disappear while the page is only half done. The page
now asks for a replacement task and finishes the remaining batches, sharing one
request across the workers that hit the gap together. API keys are still read
only in the background and never reach a page. A deliberate cancel stays final.

The same asymmetry appeared when the extension could not deliver the message
that starts a translation. A broken message port says nothing about whether the
page took the task, and the two guesses do not cost the same: destroying a task
the page is using costs the translation, while leaving one behind costs a
settings snapshot that tab teardown collects anyway.

### Cancellations say who cancelled them

Six code paths abandoned a translation and every one of them left the same
sentence, which is why the bug above took three attempts to find. An abort now
carries its origin — 页面已跳转, 标签页已关闭, 弹窗主动取消 — into the status
bar, and prints the task id and reason to the service worker console, so a
report that has already scrolled past is still readable afterwards.

### The page limit is visible and adjustable

Translation stops after a fixed number of text segments. The limit was 220, it
was not written anywhere a user could see, and a long page hitting it finished
with the same contented "已翻译 N 处内容" as a short page that had been fully
translated.

The popup now has a field for it, accepting 1 to 5000, and both the status bar
and the popup say how much was left out when the limit binds — as a lower bound
when collection itself stopped early, rather than a precise number it cannot
justify.

### Article titles are translated

A `header` inside an `article` or `section` is sectioning content, not a page
header, which is how news sites and blogs mark up a headline and standfirst.
Excluding it along with real site furniture meant the top of a story went
untranslated. Elements carrying an explicit `banner`, `contentinfo` or
`navigation` role are still skipped.

### Smaller corrections

- Restoring the original text left an empty `style` attribute on every element
  that had been translated, because removing a custom property does not remove
  the attribute holding it. A site's own `p:not([style])` rules stopped matching
  after a restore.
- A heading whose font size could not be read wrote `NaNpx`, which invalidated
  the variable and dropped the translated heading to an inherited size.
- A failure belonging to one start attempt could paint over the progress of a
  different translation that was still running normally.

See `CHANGELOG.md` for the full list.

## Installation

### Chrome / Edge

1. Download `webpage-bilingual-translator-0.1.6.zip` from this release and unzip it.
2. Open `chrome://extensions/` or `edge://extensions/`.
3. Enable Developer mode.
4. Click "Load unpacked".
5. Select the unzipped folder.
6. Refresh any page you want to translate.

Upgrading from v0.1.5 replaces the unpacked folder. The content script is
injected on demand, so a page open from before the upgrade keeps running the old
one until it is reloaded.

### Safari

Safari support is included as an Xcode project under `safari/网页双语翻译/`.

For local development:

```bash
./script/build_and_run.sh
```

For long-term everyday use, Safari requires signing with an Apple Developer
certificate.

## Configuration

Default local API settings:

```text
API URL: http://127.0.0.1:1234/v1
Model: qwen/qwen3.5-35b-a3b
```

The extension works with OpenAI-compatible `POST /chat/completions` services.
DeepSeek users should select "DeepSeek API" in the popup and enter their API key
locally in the browser extension.

If LM Studio has "Require Authentication" enabled, fill in the matching API
token in the extension.

The per-page translation limit is now in the popup and defaults to 220. Leaving
the field empty restores that default.

## Verification

The release was checked with:

```bash
npm run check
npm test
npm run package
```

The fix for the scrolling bug was confirmed against the reported reproduction —
the service worker console showed the loading flip arriving with no URL, and the
task being abandoned because of it — and the rule that ignores a bare loading
flip is covered by a test that was checked to fail against the old one.

## Known Limits

- The page limit defaults to 220 unique visible text segments and can be raised
  in the popup. Very high values cost proportionally more model time.
- Newly loaded content after scrolling can be translated by clicking the
  translate action again.
- Complex site CSS may still cause small layout differences.
- API keys are stored in browser extension local storage, which is suitable for
  personal use. Team deployments should use a backend proxy.
- The extension is not yet listed on the Chrome Web Store, so installation still
  goes through Developer mode.
- Local server detection covers five common ports. A server on any other port
  still has to be entered by hand.
- Safari still reaches local APIs through a native proxy and has no local server
  detection.
